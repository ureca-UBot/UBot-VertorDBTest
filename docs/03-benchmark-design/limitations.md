# Limitations

## 현재 결과와 아직 측정하지 않은 축

프로젝트 예상 운영 규모는 **1,000~10,000청크**입니다. 현재 비교 결과는 합성 10k·BGE-M3 1024차원·concurrency 10이며 다음 축은 아직 최종 수치가 없습니다.

- 1k 규모의 별도 측정
- 실제 프로젝트 FAQ/chunk/query 분포
- 선택에 사용하지 않은 새로운 holdout 질의
- 필요 시 성장 검증용으로 선택할 100k/1M 데이터

14개 구성 전체 파라미터 sweep은 [fairness-v2의 620개 실측](../07-results/fairness-v2-results-20260913.md)을 완료했습니다. [과거 372점](../07-results/sweep-results-20260911.md)은 다른 채점·시간 조건의 역사 자료입니다. 둘을 합치거나 최신 결과를 실서비스 검증으로 격상하지 않습니다. 100k/1M 미실시는 현재 1k~10k 프로젝트의 탈락 사유가 아닙니다.

행이나 같은 벡터를 복제해 100k라고 부르지 않습니다. 실제 입력이 들어오면 전용 스크립트가 최소 건수와 synthetic 표식을 검사합니다.

## 클라이언트 비용

타이머는 `VectorStore.search()`를 감싸므로 요청 직렬화와 응답 역직렬화가 포함됩니다. JDBC binary와 HTTP JSON/GraphQL의 비용은 다릅니다. 결과는 ANN 알고리즘만의 시간이 아니라 Spring Boot 검색 경로 시간입니다.

pgvector의 현 어댑터는 검색 요청마다 `set_config`와 벡터 SELECT를 별도 실행하므로 두 요청의 비용도 지연·QPS에 포함됩니다. 이번 수치에서 이 비용만 사후에 빼서 DB 내부 순수 검색 시간처럼 제시할 수 없습니다.

## 작은 10k 데이터

10,000 × 1024 float의 raw vector만 약 39MiB라 메모리에 들어갈 수 있는 작은 입력입니다. disk index와 대규모 그래프 차이를 일반화할 수 없습니다. 다만 프로젝트 상단 규모 10k의 탐색 비교라는 의미는 있습니다. 실제 서비스 1k~10k에서 같은 특성이 나오는지는 별도 입력으로 확인합니다.

## Recall 품질점

그리드가 성기면 0.90·0.95 참고 수준을 건너뛸 수 있습니다. 이는 실패가 아닙니다. 모든 실제 점을 보존하고 관측되지 않은 Recall 수준의 성능을 실측처럼 제시하지 않습니다.

산포도에서 Recall이 비슷한 설정끼리 p95·QPS·자원과 회차 간 퍼짐을 함께 봅니다. 높은 Recall 점을 낮은 Recall 점과 비교해 단일 속도 순위를 만들거나, 이전 fixed-target의 ±0.01 선택 규칙이 이번 전체 sweep에 실행됐다고 쓰지 않습니다. 사후 선택 결과는 탐색 후보이지 독립 검증된 승자가 아닙니다.

## 필터

기본 합성 query는 필터가 10%뿐이고 기존 tenant×status의 실제 선택도도 1/10/50%가 아닙니다. 전용 generator가 document ID hash 기반 cohort를 만들어 세 실험을 분리합니다. 합산 p95가 아니라 `filtered_*`와 `unfiltered_*`를 각각 봅니다.

## 자원 샘플

Docker stats 명령 완료 후 약 500ms 간격으로 다시 수집합니다. 명령 자체의 시간도 있으므로 정확한 500ms 주기는 아닙니다. 검색 구간 안에서 수집을 시작하고 마친 표본만 집계하며 측정 후 유휴 표본은 사용하지 않습니다. 이번 620개 측정은 모두 최소 30초·자원 표본 30개를 충족했습니다. 이는 연속 관측이 아니므로 순간 peak를 모두 포착하거나 정밀한 자원 분포를 보장하지 않습니다. OpenSearch는 8GiB 컨테이너 예산 안에 4GiB JVM 힙을 설정했으므로 Docker RAM을 실제 live heap으로 해석하지 않습니다. index size `-1`은 0이 아니라 제품 API 미지원입니다.

## warm cache

파라미터 적용 후 같은 동시성의 200요청 warm-up을 3~10회 실행하고 최근 3개 p95의 안정성을 확인합니다. 구성 안 검색 폭은 회차 시드로 섞습니다. 그런데 **170/620점은 워밍업 기준 미충족**이며, 통과했더라도 1,000요청 배치를 반복하는 본 측정의 안정성을 보증하지 않습니다. 경고점은 삭제하지 않고 산포도와 반복 분포에서 구분합니다. cold start, 장애 복구, 재색인 중 읽기, write/read 혼합, backup/restore, rolling upgrade는 별도 시험입니다.

## Milvus 진단의 사각지대

현재 진단은 본 측정 뒤 calibration 질의의 직렬·동시성 Recall과 상태 응답을 확인합니다. `verified=true`는 측정 중 모든 응답의 재현성을 보증하지 않습니다. 이번 **DISKANN 5점**에서는 동일 질의·설정의 Recall이 측정 중 달라진 기록이 확인됐으므로 원시 결과를 유지하고 재현성 확인 대상으로 표시합니다. 모든 Milvus 측정이나 전체 620점을 무효로 일반화하지 않습니다.

## 통계

이번 실행은 5회 전체 재구축과 순서 교차를 수행했습니다. 5회도 모집단의 꼬리나 넓은 신뢰구간을 추정하기에는 적습니다. median과 range는 반복 안정성 신호이지 보편적 성능 보장이 아닙니다. 5회 중 가장 좋은 값만 고르거나 경고 회차를 빼서 반복 통계의 의미를 바꾸지 않습니다.

## 실제 제품 결정

팀은 이 측정의 성능 차이가 절대적으로 크지 않다고 보고, 운영·개발 편의성을 우선해 pgvector를 선택했습니다([선정 결론](../07-results/decision.md)). 위 한계 때문에 이 선택은 "측정에서 pgvector가 가장 빨랐다"는 뜻이 아닙니다. UBot-BE의 실제 설정(Top-3, HNSW 기본 파라미터, `deleted_at` 조건)은 측정 조건과 다릅니다. 과거 단일 실행 결과는 [docs/07-results](../07-results/)에 보존하지만 현재 순위표로 사용하지 않습니다.

현재 `DecisionGate`는 holdout 상태와 Recall 0.95·p95 30ms·RAM 2GiB 등 서로 다른 조건을 하나의 `eligible`로 합칩니다. 특히 30ms와 2GiB는 합의된 서비스 SLO가 아니므로 **현재 summary의 eligible=false를 DB 실패나 구성 탈락으로 해석하지 않습니다.** 이 문서는 판정의 해석을 바로잡는 것이며 코드·기존 summary를 수정했다고 뜻하지 않습니다. 실측 무결성, 워밍업·재현성 경고, 검증 미실시, 향후 서비스 적합성을 구분해야 합니다.
