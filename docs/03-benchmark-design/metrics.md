# 측정 지표와 해석

현재 기준은 [2026-09-13 완료 fairness-v2의 620개 실측](../07-results/fairness-v2-results-20260913.md)입니다. 합성 10k·1024차원·concurrency 10에서 같은 124개 설정을 독립 재구축 5회씩 측정했습니다. 지표 이름은 CSV 기준으로 설명하며 JSON 대응 필드는 [결과 형식](../06-implementation/result-format.md)에 있습니다. 과거 372점은 별도 채점·측정 조건의 역사 자료입니다.

## Recall@10과 품질 참고선

```text
K = min(10, 필터를 만족하는 문서 수)
A = Exact K위보다 좋은 ID 집합, B = K위 경계 동점 ID 집합, R = ANN 반환 ID 집합
Actual Recall@10 = (|R∩A| + min(K−|A|, |R∩B|)) / K
```

질의별로 원본 벡터의 경계 동점을 인정한 비율을 계산하고, 정답이 있는 검색의 Recall을 평균합니다. 반환 순서는 평가하지 않습니다. 동점 허용 오차는 이번 실행에서 0입니다. 기존 `|Exact Top-K ∩ ANN Top-K| / K`는 strict-ID 보조 지표이며 `filtered_strict_id_recall`·`unfiltered_strict_id_recall`로 별도 저장합니다. [Ground Truth](ground-truth.md)에서 동점 크레딧 상한을 확인합니다. Exact 정답이 빈 질의는 평균에 1.0을 더하지 않고 빈 결과 반환 여부를 별도로 기록합니다.

| 필드 | 모집단 |
|---|---|
| actual_recall | evaluation의 필터·무필터 중 Exact 정답이 있는 검색 |
| filtered_recall | 필터 검색 중 Exact 정답이 있는 검색 |
| unfiltered_recall | 무필터 검색 중 Exact 정답이 있는 검색 |
| comparison_recall | 무필터 Recall을 우선 사용하는 보조값 |

이번 evaluation 200개는 무필터 180개·필터 20개입니다. 정답이 빈 필터 6개를 뺀 194개가 한 번의 질의 집합 실행에서 Recall 평균에 들어갑니다. 지연과 QPS에는 200개 모두 포함됩니다.

Recall 0.90과 0.95는 **수평 품질 참고선**입니다. 이번 sweep은 과거 fixed-target의 calibration 선택·목표 ±0.01 검사를 수행하지 않습니다. 산포도에서 실제 Recall이 비슷한 점의 p95·QPS·RAM을 함께 비교하되, 관측되지 않은 Recall의 성능을 보간해 실측처럼 쓰거나 서로 다른 Recall의 점을 단일 순위로 정리하지 않습니다. 사후 대표값을 설명하더라도 다른 파라미터·회차를 모두 보존하고 탐색 선택임을 밝힙니다.

## Latency

각 요청의 `VectorStore.search()` 시작부터 반환까지를 측정합니다. 요청 직렬화·네트워크·DB 검색·응답 역직렬화가 포함되며 Exact 정답 계산, Recall 후처리, 응답 검증·저장은 타이머 밖입니다. 파라미터별 index-manager 설정 변경은 별도지만 **pgvector의 매 검색 `set_config` SQL은 search 내부라 측정에 포함**됩니다. 따라서 순수 ANN 알고리즘 시간이나 DB 내부 실행 시간만 측정한 결과가 아닙니다.

| 필드 | 의미 |
|---|---|
| average_ms | 모든 측정 요청 지연의 평균 |
| p50_ms | 요청 지연의 중앙값 |
| p95_ms | 요청 지연의 95분위수; 주 산포도 X축 |
| p99_ms | 요청 지연의 99분위수 |

### 전체 지연과 필터별 지연

전체 p95는 고정한 혼합 workload의 응답 지연입니다. 필터 검색이 느리면 전체 꼬리지연에 영향을 줄 수 있습니다. 원인 분석에서는 `filtered_*`와 `unfiltered_*`를 따로 읽습니다.

| 비교 | 같은 행에서 짝지을 값 |
|---|---|
| 주 산포도 | p95_ms ↔ actual_recall |
| 무필터 검색 | unfiltered_p95_ms ↔ unfiltered_recall |
| 필터 검색 | filtered_p95_ms ↔ filtered_recall |

무필터 Recall과 전체 p95를 같은 모집단처럼 짝지으면 안 됩니다. 평균과 일부 분위수만으로 필터 경로를 판정하거나, 파라미터에 둔감한 p95만으로 인덱스 미사용을 확정하지 않습니다.

## QPS와 측정 구간

```text
QPS = 성공한 검색 요청 수 / 실제 검색 구간(초)
```

concurrency=10으로 실행한 검색 작업이 모두 끝날 때 타이머를 닫습니다. Recall 계산·응답 검증·저장·별도 진단은 제외합니다. 실패 요청의 지연도 전체 latency에 포함하지만 QPS 분자에서는 빼며, 이번 검색 실패는 0건이므로 성공 수와 `query_executions`가 같습니다. 이 값은 현재 클라이언트·부하에서 관측한 처리량이며 서버의 이론적 최대 QPS는 아닙니다.

각 점은 evaluation 200개 × measurementIterations 5, 즉 1,000요청 단위를 **최소 30초·자원 표본 30개를 모두 충족하도록** 반복합니다. 불완전한 질의 단위를 잘라내지 않아 필터 비율을 유지합니다. 실제 `query_executions`는 점마다 다르며 `measurement_time_ms`와 함께 저장합니다. QPS는 내부의 정밀 타이머로 계산하므로 정수 ms 필드로 다시 나누면 반올림 차이가 날 수 있습니다.

품질과 처리량은 함께 비교합니다. Recall이 다른 점도 trade-off 분석에 포함하며, 입력·Top-K·동시성·자원 조건이 다른 실험은 별도로 구분합니다.

## CPU와 RAM

대상 컨테이너의 Docker 표본을 합산합니다. Milvus는 본체·etcd·MinIO 합계이며 다른 DB 프로필의 PostgreSQL 원본 저장소와 클라이언트 JVM은 대상에서 제외합니다.

| 필드 | 의미 |
|---|---|
| cpu_average_percent / cpu_max_percent | 검색 구간 안 CPU 표본의 평균 / 최대 |
| ram_average_bytes / ram_max_bytes | 검색 구간 안 RAM 표본의 평균 / 최대 |
| resource_samples | 수집 시작·종료가 모두 검색 구간 안인 표본 수 |

CPU 100%는 한 코어 사용량에 해당합니다. 낮은 CPU만으로 효율을 판단하지 않고 Recall·latency·QPS를 함께 봅니다. RAM은 엔진·인덱스·메타데이터 등을 포함한 Docker 관측값입니다. OpenSearch의 미리 확보한 JVM heap을 live object 크기로 해석하지 않습니다.

수집 명령이 끝난 뒤 500ms를 기다려 다음 표본을 수집하므로 정확한 500ms 주기는 아닙니다. 검색 전 baseline은 디스크 쓰기 차이의 기준으로만 사용하며, 검색 종료 뒤 유휴 CPU·RAM 표본은 더하지 않습니다. 평균·최대는 수집한 표본의 통계이며 검색 구간 모든 순간의 값을 보장하지 않습니다.

이번 620개 점은 자원 표본이 각각 최소 30개이고 자원 수집 누락은 0개입니다. 수집 불가가 발생하면 원시값 -1과 표본 수를 그대로 남기며, 집계의 유효 표본이 없을 때는 null입니다. -1을 0이나 저자원 구성으로 해석하지 않습니다.

실행 예산은 DB 합계 **4 vCPU/8GiB**, OpenSearch JVM 힙은 그 안의 **4GiB**입니다. RAM Avg/Max는 관측 비교 지표입니다. 코드의 RAM 2GiB·p95 30ms 기본값은 미합의 SLO이므로 이번 보고서에서 구성 탈락에 사용하지 않습니다. 예산을 맞췄는지 확인하는 것과 더 적은 RAM을 썼는지 비교하는 것은 다른 질문입니다.

## 디스크와 준비 비용

| 필드 | 의미와 한계 |
|---|---|
| disk_write_bytes | baseline부터 마지막 유효 표본까지 Docker Block I/O write 증가량; 전체 검색 종료 순간까지의 쓰기를 모두 포착하지 않을 수 있음 |
| index_size_bytes | pgvector의 실제 인덱스 관계 크기 또는 OpenSearch index store 크기; 제품별 범위가 다르고 미지원은 -1 |
| time_to_index_ready_ms | drop/create·적재·index/load 준비 완료까지의 시간; 순수 ANN build 시간과 다름 |
| upsert_ms | 적재 호출 구간; 별도 지속 write 처리량 시험이 아님 |

같은 재구축을 공유하는 여러 검색 파라미터 행의 준비·적재 시간은 반복 기록된 값입니다. 행별로 더해 총 구축 시간으로 계산하지 않습니다. 원시 벡터 크기나 전체 Docker 볼륨 크기는 이 필드에서 얻을 수 없습니다.

## 같은 파라미터의 반복 통계

이번 실험은 14개 구성을 각각 5회 재구축해 124개 고정 파라미터 그룹의 반복을 얻었습니다. 같은 생성·검색 파라미터, 입력·부하·환경 조건끼리만 평균, median, p95/p99, min/max, 표본분산과 유효 표본 수를 계산합니다.

- 한 점의 `p95_ms`: 그 점 안의 검색 요청 지연에 대한 95분위수.
- 집계의 `p95_ms_median`: 같은 파라미터의 다섯 p95 값에 대한 중앙값.
- 집계의 `p95_ms_p95`: 같은 다섯 p95 값 사이의 95분위수; 합쳐진 요청의 p95가 아님.
- `sample_variance`: n−1로 나눈 표본분산.

다섯 번의 표본에서도 현재 nearest-rank p95/p99는 최대값입니다. 넓은 신뢰구간을 제공하지 않습니다. 원시 620점 산포도와 124개 설정의 5회 집계 그림을 구분하며 한쪽으로 다른 쪽을 대체하지 않습니다.

워밍업 불안정 170점과 측정 중 재현성 확인이 필요한 Milvus DISKANN 5점은 경고를 붙여 보존합니다. 예시 SLO 초과·워밍업 경고·검증 미실시·검색 오류를 하나의 실패로 합치지 않습니다. 기존 summary의 `decision.eligible`에는 미합의 기본값과 holdout 미실시가 섞여 있어 현재 선정 근거로 사용하지 않습니다. 해당 코드를 제거하거나 기존 값을 재작성했다는 의미는 아닙니다.

## 역사 자료로 읽는 예 — 2026-09-11 v1

다음은 과거 372점 실험의 Qdrant HNSW T05 **1회차**에서 선택한 설명용 점입니다. 각 행의 모든 값은 같은 과거 측정에서 가져왔으며 최신 v2 채점·측정 조건의 값이 아닙니다.

| hnsw_ef | Recall@10 | p95 ms | QPS | 평균 CPU % | 평균 RAM MiB |
|---:|---:|---:|---:|---:|---:|
| 20 | 0.941237 | 3.596 | 3831.3 | 358.57 | 107.25 |
| 120 | 0.977320 | 4.322 | 3249.4 | 396.79 | 103.05 |
| 1000 | 0.980412 | 20.444 | 1272.5 | 389.19 | 102.45 |

`hnsw_ef=120→1000`에서 이 회차의 Recall 증가는 약 0.0031이고 p95는 4.322→20.444ms로 늘었습니다. 어떤 탐색 폭의 비용이 유용한지를 실제 품질 변화와 함께 판단하는 예입니다. 표에 생략한 파라미터와 다른 회차도 [전체 산포도](../07-results/assets/sweep-20260911-220549/scatter-recall-latency-all-372.svg)에 모두 남아 있습니다.

이 역사 예시를 최신 620점에 합산하거나 다른 데이터 규모·운영 환경의 제품 순위로 일반화하지 않습니다. 제약은 [limitations.md](limitations.md), 최신 산포도는 [fairness-v2 결과 보고서](../07-results/fairness-v2-results-20260913.md)를 확인합니다.
